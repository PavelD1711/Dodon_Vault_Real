# Технический анализ базы OpenClaw для multi-agent

Что поддерживает наша текущая инсталляция OpenClaw, что придётся доработать.

## Что есть сейчас

### 1. Один агент `main`

Проверено: `agents_list` → возвращает только одну сущность:

```json
{
  "id": "main",
  "configured": true,
  "model": "genspark-llm-proxy/claude-sonnet-4-6"
}
```

Значит `agentId` инфраструктура **есть**, но настроен только один агент.

### 2. `sessions_spawn` — одноразовые sub-agents

Работает. Позволяет создать «дочернюю сессию» под задачу — она получает задание, отрабатывает, возвращает результат.

**Хорошо для:** разовых узких задач.
**Плохо для:** долгоживущих личностей-экспертов.

### 3. `sessions_send` — межагентная коммуникация

Инструмент есть. Как только у нас будет >1 агента — они смогут переписываться программно.

### 4. `sessions_list` — visibility между сессиями

Есть, но visibility ограниченная (например, я не вижу истории Telegram-групп, кроме той, где сейчас говорю).

## Что нужно сделать для Уровня 2

### A. Регистрация новых `agentId` в конфиге OpenClaw

Изучить документацию OpenClaw про то, как добавляется новый агент:
- `~/.openclaw/openclaw.json` — где секция про агентов?
- Или отдельные конфиг-файлы (`~/.openclaw/agents/<agentId>.yaml`)?

Для каждого нового агента задать:
- `agentId` (уникальный, kebab-case)
- `name` (человекочитаемое)
- `systemPrompt` (роль, личность, границы)
- `model` (какая LLM)
- `tools.allow` / `tools.deny` (какие инструменты доступны)
- `channels` (какие Telegram-группы видит)

### B. Маршрутизация Telegram

Два варианта:

**Вариант B1: Один Telegram-бот, разные роли по группам**
- Один бот-токен, но в конфиге маршрутизация: группа `-5521808848` → агент `time-assistant`
- Плюсы: не нужны отдельные боты
- Минусы: у всех агентов один аватар/имя в Telegram

**Вариант B2: Отдельный Telegram-бот на каждого агента**
- Каждый агент — свой @-username, аватар
- Плюсы: чёткая идентификация, психологически удобнее
- Минусы: надо регистрировать ботов, добавлять в группы

### C. Синхронизация состояния

- Общий vault ← читают все агенты, пишут в свои зоны
- Общий memory ← читают все, пишут все (важные факты)
- Правило владельца: у каждого файла — один агент-owner
- Locking? — думать когда упрёмся

### D. Наблюдаемость

- Дашборд: какой агент чем занят, сколько токенов ест
- Логи взаимодействий агентов (`sessions_send` history)
- Алерты о сбоях
