# Алгоритм разбора проектов

## При закрытии с `closed_fail` — обязательный разбор

Когда проект закрывается со статусом `closed_fail`, инициировать разбор:

1. Что планировалось (goal / KR)?
2. Что случилось по факту?
3. Корневая причина провала?
4. Какой риск это обнажает?
5. Нужен ли отдельный проект по устранению?

Результат разбора → `Проектный офис/Разборы/<название>.md`
Риск → `Проектный офис/Риски/Реестр рисков.md`

---

## При закрытии реактивного проекта — разбор корневой причины

После закрытия любого `type: reactive`:

1. Почему возник этот пожар?
2. Что его спровоцировало (системная причина)?
3. Риск зафиксирован?
4. Нужен проактивный проект по устранению?

Результат → `Проектный офис/Разборы/<название>.md`
Риск → `Проектный офис/Риски/Реестр рисков.md`

---

## Аналитика (после упаковки ~250 проектов)

Запланировать отдельную сессию — анализ паттернов, провалов, распределения по `life_area`, людям, временным циклам.

Что увидим:
- Паттерны провалов (типы, люди, причины)
- Куда уходит энергия (реактивные vs стратегические)
- Дисбаланс по зонам жизни (`life_area`)
- Делегирование vs ручное управление Павла
- Временны́е циклы открытия/закрытия проектов
