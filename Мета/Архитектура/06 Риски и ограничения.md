# Риски и ограничения

## 1. Стоимость (LLM-токены)

**Риск:** каждый агент — это отдельные вызовы LLM. Если Time Assistant + Финдир + Инкомтранс + Оркестратор — то на одну сложную задачу может уйти в 4× токенов относительно моно-агента.

**Митигация:**
- Оценить стоимость на этапе B (реальные цифры до разворачивания)
- Использовать более дешёвые модели для узких агентов (например `claude-sonnet` вместо `opus`)
- Кэширование system-prompts (у нас 97% cache hit — работает хорошо)
- Правило: диспетчер не привлекает узких агентов, если может ответить сам

## 2. Дисциплина ролей

**Риск:** легко скатиться в «все обо всём» — Инкомтранс Expert начинает советовать по мессериашу, Time Assistant рассуждает о ставках аренды.

**Митигация:**
- Чёткий system prompt: «отвечаешь только по своей области, вне — переадресуй»
- В system prompt перечислить других агентов и как их вызывать
- Ретро раз в месяц: где кто вышел за границы

## 3. Дрейф личности («смена паспортов»)

**Риск:** если у меня много ролей — я могу путать «в какой роли говорю».

**Митигация:**
- Каждый агент — **отдельный `agentId`** (не профиль!) в Уровне 2
- В начале ответа — self-check: «я сейчас = <роль>»
- Разные аватары и имена в Telegram помогают удерживать

## 4. Синхронизация состояния файлов

**Риск:** два агента одновременно пишут в один файл vault → git conflict.

**Митигация:**
- Правило владельца: у каждого файла один агент-owner (пишет только он)
- Остальные — только читают
- Изменения — через PR-стиль (агент А просит агента B внести правку)
- Или еще проще: разделение зон записи по папкам

## 5. Ты (Павел) как центр

**Риск:** оркестратор становится «bottleneck» — все запросы через него, задержки, потеря контекста.

**Митигация:**
- Прямой доступ к любому агенту — Павел может обратиться напрямую
- Диспетчер только для сложных мульти-агентских задач
- Регламент: простой вопрос → прямо к специалисту, сложный → к диспетчеру

## 6. Отладка и наблюдаемость

**Риск:** когда что-то идёт не так — непонятно, кто виноват (какой агент, какая передача).

**Митигация:**
- Лог всех `sessions_send` вызовов
- Каждое сообщение метится агент-автором
- Дашборд состояния: кто активен, чем занят, сколько токенов

## 7. Consistency vs Specialization tradeoff

**Риск:** узкие агенты дают лучший ответ в области, но менее «в общем контексте Павла».

**Митигация:**
- Общий memory + vault — все агенты видят контекст
- Регулярный «синк» — оркестратор напоминает всем последние ключевые решения
- Правило: важные факты обо всех проектах → в общий memory

## 8. Масштабирование команды

**Риск:** сегодня 5 агентов, завтра 15, послезавтра «зоопарк».

**Митигация:**
- Портрет команды **до** разворачивания
- Регламент: чтобы завести нового агента — must-have роль, приоритет, метрики
- Ретро раз в квартал: кого удалить, кого добавить, кого объединить

## 9. Vendor lock-in

**Риск:** мы завязаны на архитектуру OpenClaw. Если она поменяется — переделывать.

**Митигация:**
- system-prompts и портрет агентов — храним в vault (в markdown, портируемо)
- Конфиги OpenClaw в git backup
- Готовность к миграции если что
